# P4「导演策划 / 角色与场景设计」审阅草案

> 状态：仅供讨论的方案草案，不是已批准的产品规范，也不代表已修改现有流程、Plugin、MCP、Skill 或项目数据。
>
> 本草案只细化 P4。P1–P3、Auto / 分步、原生 Skill / Canvas 两组模式选择均按已确认方向保留；所有未获确认的产品政策均标记为“待用户确认”。

## 1. P4 的定位

P4 是正式生成前的**文字导演策划阶段**。它把 P1–P3 已确定的内容、叙事角色和创作约束，转化为后续图像、视频、语音、音乐可以直接消费的创作设计依据，尽可能在生成前锁定全片与逐个“分镜 / Storyboard unit”的判断。

P4 本身：

- 不生成正式角色图、场景图、关键画面、Storyboard、视频、语音或音乐；
- 不使用“镜头设计卡”；以分镜 / Storyboard unit 作为主要列，但不在单个 unit 内再按子镜头或画格拆列；
- 不把研究过程、模型思考过程或验证动作创建为 Text Node；
- “关键画面”只以文字描述画面方向、连续性锚点和后续提示词约束；
- Gemini 负责主要文本策划，GLM 负责审核、校正、一致性检查和去 AI 化；
- Canvas 模式中，所有 Gemini 策划、GLM 审核及后续修订都必须通过 Canvas 已支持的 Text Config 节点运行，并由运行时生成相应 Result Text Node；MCP 不得在 Canvas 外完成内容后直接写入一个 Text Node 伪装成生成结果；
- 原生模式把语义相同的内容记录到项目 Markdown，不能因后端不同而缺项。

### 1.1 建议的上游输入

- P1：Topic、受众、片长/画幅等项目约束、生产控制模式、执行后端、用户明确的创作偏好与禁区；
- P2：事实依据、主题分析、内容大纲、最终脚本及已确认的事实边界；
- P3：叙事结构、已有的分镜初分及其涉及场景、叙事角色清单、已有正式角色/角色资源及其他已锁定设定；
- 可用资产索引：已有角色资料、视觉参考、品牌规范、允许复用的提示词及其版本。

> 待用户确认：P3 到 P4 的精确边界。建议 P3 只需交付“叙事上需要谁、发生什么、在哪里发生”的可靠输入，P4 再把角色和场景落实为可生产设计；但这不能在未确认前写成正式政策。

### 1.2 建议的阶段产出

1. 全片通用导演设计包；
2. 统一角色总体设计包（每个角色一份）；
3. 全片世界、场景母体与共用道具规则；
4. 分镜 / Storyboard unit 索引与逐分镜导演设计包（每个 unit 一份，一个 unit 可涉及多个场景）；
5. 跨分镜连续性与冲突审核记录；
6. 提示词资产台账：已复用、需改造、待新建、用途、适用阶段和版本要求；
7. P4 锁定清单与仍待人工决策的问题。

## 2. Canvas 总体布局

建议把 P4 组织成三条泳道，按依赖由左向右排列。G/Q 列承载全片与审核工作单元；U 列明确以分镜 / Storyboard unit 为主，每列是一份完整文字导演策划，不是“镜头设计卡”。

| 泳道 | Canvas 列 | 内容 |
|---|---|---|
| A. 全片通用设计 | G0–G6 | 输入边界、导演总纲、节奏、视听语言、角色母版、世界/场景母体、共用道具与连续性规则 |
| B. 分镜 / Storyboard unit 设计 | U0、U01…Unn | 分镜单元索引，以及每个 unit 的完整文字生成—审核—修订工作列；一个 unit 可覆盖一个或多个场景 |
| C. 审核与锁定 | Q0–Q2 | GLM 跨分镜审核、提示词资产台账、人工锁定与遗留问题 |

依赖顺序建议为：

`G0 → G1/G2/G3/G4 → G5/G6 → U0 → U01…Unn → Q0 → Q1 → Q2`

- `G1–G4` 可在共同输入锁定后并行起草，但必须相互校准后才能进入分镜单元设计；
- `G5` 统一角色总体设计必须先于任何分镜中的角色状态或风格变体；
- 每个分镜 / Storyboard unit 使用一个工作列，列内至少包含上游输入 Text、System Prompt Text、Gemini Text Config、Gemini 草案 Result Text、GLM 审核 Text Config 和 GLM 审核 Result Text；需要校正时继续建立 GLM 校正 Text Config 与校正 Result Text，需要响应新的创作反馈时才使用 Gemini 修订 Config；最终被接受的 Result Text 才是该 unit 的当前导演策划产物；
- 分镜单元之间只记录真实语义依赖，例如动作延续、服装状态继承、关键道具转移、场景转换或情绪状态承接；是否用 Canvas 连线表达仍为**待用户确认**；
- 研究和验证是生成/审核这些文本的工作动作，不单独建立“研究进度 Text Node”或“验证进度 Text Node”。但研究依据若作为模型输入，应进入真实的输入 Text Node；审核结论则必须由审核 Config 运行后输出为真实 Result Text Node。

### 2.1 Canvas 文字执行硬规则

Canvas 模式中的 P4 文字内容必须遵循以下执行契约：

1. **输入可见**：P1–P3 来源、用户要求、角色/场景母体、前序分镜结果和人工反馈，以真实 Text Node 作为输入；System Prompt 也是可见的 Text Node。
2. **调用可见**：Gemini 策划必须由 Gemini 对应的 Text Config Node 运行；GLM 审核、校正和去 AI 化必须由 GLM 对应的 Text Config Node 运行；任何新一轮修订也必须使用独立或明确复用的 Text Config Node 再运行。
3. **结果由运行时产生**：草案、审核意见、修订稿和复审意见都是 Config 的 Result Text Node。MCP 不得直接填写或覆盖这些生成结果的正文。
4. **连接真实**：普通输入 Text、上游 Result Text 和 System Prompt Text 必须按 Canvas 当前的连接/引用契约真实进入对应 Config；不能只在 metadata 中声称使用了某项输入。
5. **校正走新一轮生成**：GLM 审核发现可直接校正的问题后，MCP 把“Gemini 草案 Result + GLM 审核 Result + 已接受的人工反馈”连接到 GLM 校正 Config，再运行得到校正 Result；不能由 MCP 直接修改草案 Result Text。若反馈要求重新做创作判断，则由 Gemini 修订 Config 生成新稿，再交给 GLM 审核/校正。
6. **复审同理**：需要复审时，由 GLM 复审 Config 消费当前校正/修订 Result 和必要上游，输出新的审核 Result，直到通过或进入人工裁决。
7. **可追溯、可重跑**：每个 Result 都保留其输入、System Prompt、Config、模型选择和运行快照；输入变化只使受影响的结果及下游过期。
8. **MCP 边界**：MCP 负责创建/更新输入与 System Prompt、创建/配置/连接/运行 Config、查询状态、组织列和标记当前有效结果；模型生成正文只能来自 Canvas 节点运行时。

单个工作单元的推荐执行链：

```text
上游/用户输入 Text ─┐
Gemini System Text ──┴→ Gemini Text Config → Gemini 草案 Result Text

上游约束 Text ──────┐
Gemini 草案 Result ──┼→ GLM 审核 Text Config → GLM 审核 Result Text
GLM System Text ─────┘

Gemini 草案 Result ──┐
GLM 审核 Result ─────┼→ GLM 校正 Text Config → GLM 校正 Result Text（当前候选）
人工反馈 Text（可选）┘

当前候选 Result ─────┐
GLM 复审 System Text ┴→ GLM 复审 Text Config → GLM 复审 Result Text
```

若初次 GLM 审核直接通过，Gemini 草案 Result 可以成为当前有效产物，不必为了形式强制生成一次校正稿。若人工反馈改变了创意方向，则另走“当前候选 Result + 人工反馈 Text → Gemini 修订 Config → Gemini 修订 Result → GLM 审核/校正”的可见链路。所谓“每个 unit 一个策划产物”，指最终只选定一个当前有效 Result Text 作为下游入口，不代表整个 unit 只有一个节点。

## 3. 全片通用设计列

### G0 — P4 输入、边界与冲突清单

- **目标**：把 P1–P3 的已确认事实、硬约束、可创作空间和当前缺口整理为 P4 的唯一工作入口，防止导演策划悄悄改写上游。
- **上游输入**：P1–P3 全部有效产物、用户补充、已有资产索引。
- **文字产出**：项目摘要；硬约束；允许发挥项；不可改写项；已有/缺失资产；上游冲突；需用户裁决项；P4 完成定义。
- **人工确认**：上游冲突如何处理；哪些偏好是硬约束；哪些缺口可由模型合理补全。
- **Gemini 职责**：抽取并结构化输入，只陈述有依据的信息；发现冲突时并列呈现，不自行裁决。
- **GLM 职责**：检查遗漏、事实漂移、脚本改写、虚构设定和约束冲突；把空泛表述改为可验证条件。
- **提示词资产**：`P4-输入归一与冲突识别`——**待新建**，用于稳定提取边界；如已有同等模板则优先复用并登记版本。

### G1 — 导演总纲、世界观与情绪弧

- **目标**：定义全片为什么这样拍、观众应如何理解和感受，以及世界在视觉和行为上的基本规律。
- **上游输入**：G0、主题分析、最终脚本、受众与内容目标。
- **文字产出**：导演意图；核心命题；观众体验目标；世界观与时空规则；现实/夸张尺度；叙事视角；整体情绪基调与变化弧；喜剧/科普/戏剧表达边界；必须避免的误读与陈词滥调。
- **人工确认**：导演意图、世界规则、总体情绪是否符合品牌与受众；哪些表达禁区不可越过。
- **Gemini 职责**：把脚本转成具体、统一、可执行的导演判断，不增加未经上游支持的核心情节或事实。
- **GLM 职责**：检查主题偏移、价值表达、情绪操纵过度、套话和“宏大但无法执行”的 AI 文风。
- **提示词资产**：`P4-全片导演总纲`——**待新建**；可参考既有内容策划字段，但不能直接把内容分析模板当成导演设计模板。

### G2 — 全片节奏、信息密度与分镜推进

- **目标**：在不制作镜头卡的前提下，确定全片段落节奏、信息释放、情绪起伏和分镜单元之间的推进逻辑。
- **上游输入**：G0、G1、内容大纲、最终脚本、目标片长。
- **文字产出**：开场抓力；段落功能；信息密度曲线；快慢转换；情绪峰谷；解释、停顿和留白；场景进入/退出原则；转场的叙事目的；容易疲劳或理解困难的位置。
- **人工确认**：节奏是否符合受众；是否允许改动段落顺序或只可提出建议；互动模式下是否在此处暂停。
- **Gemini 职责**：给出分镜单元级节奏方案和理由，不伪造精确音频时长，也不把一个 unit 机械拆成逐镜头卡。
- **GLM 职责**：检查节奏建议是否与脚本信息量、受众理解成本和总片长一致；删去机械化“三段式”套模板痕迹。
- **提示词资产**：既有节奏规范可作为**候选复用依据**；`P4-分镜单元级节奏设计`是否已有等价资产需盘点，缺失则**待新建**。

### G3 — 全片视觉、镜头与空间语言

- **目标**：建立后续所有场景共同遵守的视觉语法，而不是设计具体镜头清单。
- **上游输入**：G0、G1、G2、用户视觉偏好、已有品牌/角色参考。
- **文字产出**：媒介与渲染方向；形体语言；色彩系统；材质与光线；构图和负空间；画幅安全区；视角偏好；机位高度/距离原则；透视与焦段倾向；景深原则；静态/运动构图；运镜使用与禁用条件；场景间视觉区分与统一规则；负面约束。
- **人工确认**：整体美术方向、写实程度、视觉参考的使用边界、运镜克制程度和明确禁用项。
- **Gemini 职责**：把审美词汇转成可以在后续提示词中验证的画面条件；说明何时适用，不堆叠互相冲突的风格标签。
- **GLM 职责**：检查风格拼贴、摄影术语误用、相互矛盾的光线/景深/运镜要求，以及只有形容词没有执行条件的内容。
- **提示词资产**：`P4-全片视觉与镜头语言`——**待新建**；现有 Storyboard 提示词不适用于本列，不能作为 P4 默认模板。

### G4 — 全片动作、人物动效、环境动效与声音语言

- **目标**：统一“画面如何活起来”和“声音如何参与叙事”的规则，为后续视频、语音和音乐阶段提供文字依据。
- **上游输入**：G0–G3、角色资料、最终脚本。
- **文字产出**：人物动作尺度与节奏；表情/眼神/重心/手势规律；人物动效原则；画面和环境动效（风、尘、液体、粒子、光影、机械、群体等）；静止的使用；动作与转场的关系；对白/旁白表演总则；音乐功能、风格范围和段落变化；环境音层次；关键音效策略；声音留白；声画同步/反差/先后关系；禁用的声音俗套。
- **人工确认**：动作夸张度；是否允许 P4 定义对白/旁白表演方向；音乐风格和版权/品牌限制；声音是否服务科普信息而非抢夺注意力。
- **Gemini 职责**：从叙事与角色出发建立可执行的动作和声音规则，不生成正式语音/音乐提示词成品。
- **GLM 职责**：检查动作是否违反角色/物理/空间逻辑，声音建议是否遮挡对白、制造错误情绪或使用空泛“电影感”。
- **提示词资产**：`P4-动作与画面动效设计`、`P4-声音导演设计`——均**待新建**；既有情景化语音规范可作为后续衔接参考，但不能替代本列的全片声音设计。

### G5 — 统一角色总体设计（每个角色一份）

- **目标**：把叙事角色落实为稳定、可生成、可跨分镜复用的生产资产定义，先锁定角色母版，再允许每个分镜按叙事需要定义人物状态或风格变体。
- **上游输入**：G0、G1、G3、G4、正式角色/NPC资料、已有角色图片或角色库信息、脚本中的行为证据。
- **文字产出**：
  - 身份与叙事功能；不可改变的识别锚点；年龄感、体型、比例、轮廓、面部结构；
  - 发型/毛发、肤色/表面、服装结构、材质、配色、鞋履、固定配件；
  - 性格外显方式、站姿、重心、动作习惯、表情范围与禁区；
  - 与全片视觉语言的对应关系；已存在资源的复用方式；连续性要求；负面约束；
  - **四视图文字规格**：左侧一张大幅半身主图；右侧依次为正面全身、侧面全身、背面全身；四个区域保持身份、比例、服装、材质和配色完全一致，且右侧三个全身视图完整不裁切；
  - 后续正式角色参考图的生成目的、输入参考、必须保留项、允许探索项和验收点。
- **人工确认**：每个角色的识别锚点、主服装、比例、风格、固定配件；左侧半身主图的具体角度/表情/姿态；旧角色资源是否允许改造。
- **Gemini 职责**：基于叙事证据起草生产级角色定义，区分永久属性、默认造型和可变化项；不能把某个分镜内的临时造型写成角色永久属性。
- **GLM 职责**：检查刻板印象、年龄/身份冲突、描述不可视化、四个视图不一致风险、过量配件和后续生成难以稳定复现的问题；进行去 AI 化措辞。
- **提示词资产**：现有“三视图固定基础提示词”只能作为结构一致性语言的**改造候选**，不能原样复用；`四视图角色设计基础提示词`为明确的**待建设资产**，用途是后续生成上述固定布局的角色参考图。另需盘点是否已有`生产级角色母版设计`文本提示词，缺失则**待新建**。

### G6 — 世界、场景母体、共用道具与连续性规则

- **目标**：在逐分镜设计之前建立全片共享的空间、物件和连续性母规则，避免每个分镜单元独立发明角色世界和场景规则。
- **上游输入**：G0–G5、脚本、场景初步划分、已有场景/道具资源。
- **文字产出**：世界尺度与物理规则；主要地点母体；空间拓扑；建筑/自然结构；通用光线与时间规则；材质库；共用家具/大型道具；标志物；可重复出现的图形/颜色；道具尺寸与持握关系；角色—场景比例；服装、污损、时间、天气、道具去向等连续性状态；禁止漂移项。
- **人工确认**：主要地点是否需要稳定复用；哪些道具是叙事关键资产；哪些规则允许场景化变体。
- **Gemini 职责**：把场景共同项抽成母规则并建立连续性清单，不提前生成具体场景图或镜头清单。
- **GLM 职责**：检查空间不可能、道具尺寸/用途冲突、场景重复而无区分、以及规则多到无法生产的问题。
- **提示词资产**：既有故事场景规范中的空间、光线、材质、道具字段可**选择性复用**；`P4-世界与场景母体设计`、`P4-连续性状态提取`若无等价资产则**待新建**。

## 4. 分镜 / Storyboard unit 设计列

本区以**单个分镜需要一次性确认的完整内容**为主要拆分口径。它不以场景为主键：一个分镜可以只发生在一个场景，也可以包含场景切换、想象/现实切换、内外空间转换或多个关联场景。场景是分镜设计包内部需要说明的内容，不是主列。

### U0 — 分镜 / Storyboard unit 索引与依赖图

- **目标**：建立 P4 的主要确认单元，明确每个分镜应作为一个整体回答什么创作问题，以及它如何承接前后分镜。
- **上游输入**：G0–G6、最终脚本、叙事段落结构、已知的分镜划分或 Storyboard unit 草案。
- **文字产出**：每个 unit 的稳定编号、覆盖的脚本范围、叙事/知识目的、必须呈现的信息、涉及的一个或多个场景、参与角色、进入状态、离开状态、核心变化、前后分镜依赖、复用的角色/场景/道具母版、设计优先级和当前缺口。
- **人工确认**：什么内容应作为一个分镜整体确认；分镜之间的合并/拆分；跨场景内容是否仍属于同一 unit；分镜顺序和连续性关系。
- **Gemini 职责**：以“需要共同确认的一组创作判断”为依据提出 unit 划分并说明理由；场景变化不自动等于新 unit，也不为满足固定秒数机械拆分。
- **GLM 职责**：检查脚本覆盖遗漏、重复 unit、确认边界过大或过碎、场景切换无交代、角色/道具凭空出现，以及相邻分镜状态无法衔接。
- **提示词资产**：`P4-分镜单元识别与依赖图`——**待新建**或从现有分镜拆解资产改造；新版本必须服务 P4 文字确认，不直接生成正式 Storyboard 或按画格输出镜头卡。

### U01…Unn — 单分镜导演设计包（每个 Storyboard unit 一个节点工作列）

- **目标**：在一个统一文字包中锁定单个分镜需要确认的人物状态/变体、一个或多个场景与小道具、画面方向、情绪与节奏、表演动作、镜头语言、机位/景深/运镜、环境动效、音乐/环境音/音效和提示词约束，成为后续正式生成的共同来源。
- **上游输入**：对应 U0 条目、G1–G6、最终脚本、角色母版、涉及的地点/道具母版、前一分镜离开状态和连续性要求。
- **文字产出**：Gemini Text Config 先按下节固定模板输出草案 Result Text，再由 GLM 审核/校正 Config 输出审核及必要的校正 Result Text；不输出“镜头设计卡”、正式 Storyboard 图片、逐画格生成稿、正式图像提示词或正式 H3 Prompt。
- **人工确认**：分镜目的；人物状态与变体；涉及的场景及场景转换；小型道具；画面方向；情绪与节奏；表演动作；镜头语言；机位/景深/运镜；环境动效；声音策略；允许与禁止的创作变化。
- **Gemini 职责**：形成完整、具体、相互一致的单分镜导演方案；一个 unit 涉及多个场景时必须说明切换逻辑和连续性；所有角色变体必须回指母版；不确定内容显式标注，不用“可适当”“高级感”等空话逃避决策。
- **GLM 职责**：逐项核对脚本与全片规则；检查角色身份漂移、跨场景跳变、动作不可执行、摄影术语冲突、声音与画面争夺注意力、画面方向过于抽象；做去 AI 化和冗余压缩。
- **提示词资产**：`P4-单分镜导演设计包`、`P4-分镜人物状态变体/场景/小道具`、`P4-分镜画面方向文字约束`——建议作为三个可组合模板，均需先盘点，缺失则**待新建**。

### 画面方向与 Storyboard unit 的边界

画面方向是“这个分镜后续必须朝什么视觉结果生成”的文字锚点。即使以 Storyboard unit 分组，P4 仍不正式出图，也不产出“镜头设计卡”或完整逐格 Storyboard：

- 可以写构图、镜头语言、机位、景深、运镜、动作状态、环境动效、光色、必须/禁止元素和连续性；
- 可以描述 unit 内需要呈现的多个关键状态，但不要求另拆子镜头编号、精确秒数或每镜头生成参数；
- 一个 unit 可有一个或多个画面方向/关键画面文字锚点，数量由信息、动作、空间与场景切换需要决定，不机械固定；
- 一个 unit 涉及多个场景时，必须分别说明各场景画面条件以及场景之间的转换和共同约束；
- 后续正式提示词必须引用这些约束，若主动偏离则需要说明原因并重新确认受影响项。

> 待用户确认：每个 Storyboard unit 默认至少需要几个画面方向/关键状态；什么情况下 P4 文字应继续细化，什么情况下留给后续正式 Storyboard 阶段决定。

## 5. 审核、提示词资产与锁定列

### Q0 — GLM 跨分镜一致性、可生产性与去 AI 化审核

- **目标**：不只审单个节点，还要从全片视角发现跨节点矛盾，给出可执行修订建议。
- **上游输入**：G0–G6、U0、全部分镜设计包、上游事实与脚本。
- **文字产出**：GLM 审核 Config 输出问题清单，至少按事实/主题、角色身份、角色变体、空间、时间/天气、光色、道具去向、动作、机位/景深/运镜、声音、风格、生产难度和 AI 文风分类；每条含严重级别、证据位置、影响范围、建议修订和是否需用户裁决。需校正时，GLM 校正 Config 另输出完整校正 Result Text。
- **人工确认**：创作分歧、跨分镜取舍和高风险修订；确定哪些审核意见进入 GLM 校正输入，哪些涉及创作方向而需要 Gemini 新一轮策划或用户裁决。
- **Gemini 职责**：负责首次策划；只有反馈改变创作判断时才通过 Gemini 修订 Config 生成新 Result，并保持改动范围可追踪；不能以新创意掩盖审核问题。
- **GLM 职责**：通过 GLM 审核 Config 输出审核 Result；通过 GLM 校正 Config 执行已接受的校正和去 AI 化并输出新的完整 Result Text。不得由 MCP 直接把 GLM 意见写进 Gemini Result，也不得擅自改变已确认创作意图。
- **提示词资产**：`P4-GLM单节点审核`、`P4-GLM跨分镜连续性审核`、`P4-GLM去AI化修订`——需盘点；没有满足 P4 字段和权责边界的版本时均列为**待建设资产**。

### Q1 — 提示词资产台账

- **目标**：保证所有提示词资产有明确来源、用途、版本和缺口，不在执行时临时拼凑。
- **上游输入**：所有 G/U/Q 工作单元、现有提示词库清单。
- **文字产出**：资产名、状态（复用/改造/待新建/弃用候选）、当前版本、责任模型、用途、输入、输出、适用阶段、引用位置、测试/验收要求和阻塞项。
- **人工确认**：复用与改造的判定；资产命名/版本政策；哪些提示词必须先审批才能进入后续阶段。
- **Gemini 职责**：识别每个设计输出需要什么提示词，不虚构“已存在”状态。
- **GLM 职责**：检查提示词之间职责重叠、矛盾、遗漏和模型角色混用。
- **提示词资产**：本列使用的`提示词资产盘点与缺口登记模板`本身如不存在，也应列为**待新建**。

### Q2 — P4 人工锁定包与下游交接

- **目标**：明确哪些创作判断已锁定、哪些仍开放、哪些资产缺口阻止进入后续正式生成。
- **上游输入**：Q0 已处理结果、Q1、全部最终 G/U 节点。
- **文字产出**：锁定项；开放项；待确认项；提示词资产缺口；下游消费映射；变更影响范围；版本/日期；人工确认记录。
- **人工确认**：是否通过 P4；未解决项能否带风险进入下游；P4 变更后哪些下游内容必须失效。
- **Gemini 职责**：通过交接摘要 Text Config 生成简洁交接 Result 与下游引用索引，不再引入新创意。
- **GLM 职责**：通过审核 Text Config 确认交接 Result 与正文一致、无未登记矛盾、无把“建议”伪装成“已确认”的表述；校正仍须由 Config 运行产生新 Result。
- **提示词资产**：`P4-锁定与下游交接摘要`——**待新建**或复用现有阶段交接模板。

> 待用户确认：P4 是否新增正式人工门禁；Auto 模式是否自动通过所有非强制项，还是角色母版、分镜画面方向与高风险冲突仍需人工确认。

## 6. Canvas Text Node 与原生 Markdown 的一一映射

### 6.1 Canvas 模式

- 每个 G/U/Q 工作单元是一个可独立运行和重跑的**节点工作列**，不是一个由 MCP 直接填写的 Text Node。每个分镜 / Storyboard unit 使用一个主列，即使该 unit 涉及多个场景也不按场景另拆主列。
- 列内按真实执行顺序放置输入 Text、System Prompt Text、Gemini Text Config、Gemini Result Text、GLM 审核/校正 Text Config 和相应 Result Text；人工反馈需要参与下一轮时也使用真实输入 Text Node。
- MCP 负责读取必要上游，创建/更新输入 Text 与 System Prompt Text，创建/配置/连接/运行 Text Config，查询运行状态，标记当前有效 Result，并按三条泳道组织位置。MCP 不得在 Canvas 外生成/修改正文后直接创建“最终 Text Node”。
- 生成 Result Text 的内容归 Canvas 节点运行时所有。重跑、校正或响应反馈时必须再次运行相应 Config；旧 Result 的保留和当前有效版本标记应遵循 Canvas 现有结果/快照契约。
- 建议工作列和节点使用稳定语义标识，如 `P4-G3-*`、`P4-CHAR-<characterId>-*`、`P4-UNIT-<storyboardUnitId>-*`、`P4-Q0-*`；具体 metadata 字段、是否沿用现有 `shotId` 命名和是否需要 MCP 能力变更属于实现设计，本草案不决定。
- 连接必须表达真实模型输入、审核、校正或继承依赖，不为了排版制造连接。System Prompt 依 Canvas 规则只连接 Config；普通来源按 Canvas composer 引用与真实连接契约进入 Config。
- 研究和事实核验动作仍不建“进度节点”；但被模型实际消费的研究结论必须成为输入 Text，GLM 审核结论必须成为审核 Config 的 Result Text。

### 6.2 原生 Skill 模式

建议以同样的稳定章节 ID 记录到项目 Markdown，确保与 Canvas 语义一致。可采用：

```text
P4-导演策划/
├── P4-总览与锁定.md
├── 全片通用设计.md
├── 角色总体设计.md
├── 分镜索引.md
├── 分镜设计/
│   ├── U01-<分镜名>.md
│   └── U02-<分镜名>.md
├── GLM审核.md
└── 提示词资产台账.md
```

这只是便于审阅的目录建议，不是已决定的文件政策。若项目希望减少文件，也可以把同样内容合并为一个 `P4-导演策划.md`，但章节 ID、字段和语义不得丢失。

> 待用户确认：原生模式采用单一 Markdown 还是按角色/分镜单元拆分多文件；Canvas 与原生之间是否需要可逆导入/导出，或只要求语义一致。

## 7. 建议的审核顺序

1. 审 G0，先解决输入冲突；
2. 审 G1–G4，锁定全片导演、节奏和视听语言；
3. 逐个审 G5 角色母版及四视图文字规格；
4. 审 G6 和 U0，确认世界/场景母体、分镜单元划分及依赖；
5. 逐分镜审 U01…Unn，重点看人物状态/变体、涉及场景、小型道具、画面方向、动作、镜头语言和声音；
6. GLM 执行 Q0 跨分镜审核，Gemini 只修订被接受的问题；
7. 审 Q1 提示词资产缺口；
8. 在 Q2 锁定 P4 并交给后续正式生成阶段。

## 8. 集中待用户确认的问题

1. **P3/P4 边界**：P3 应交付到“叙事角色与分镜初分”，还是仍保留一部分生产级角色/场景设计？
2. **P4 门禁**：P4 是否是正式人工确认阶段；Auto 与分步模式分别如何处理？
3. **分镜单元定义**：以脚本范围、叙事/知识目的、需要共同确认的创作判断，还是后续 Storyboard 生产边界作为主要拆分依据？一个 unit 跨多个场景时，何种复杂度必须再拆分？
4. **四视图主图**：左侧大半身主图采用正面、3/4 侧面还是由角色气质决定；是否允许姿态和表情变化？
5. **四视图侧面方向**：固定左侧面还是右侧面；这会影响提示词资产的确定性。
6. **人物状态/变体确认**：每个分镜中的人物状态或变体都需人工确认，还是只有偏离角色母版/关键分镜时确认？
7. **画面方向数量**：每个 Storyboard unit 至少一个画面方向/关键状态，还是按信息、动作和跨场景需要创建；是否设置建议上限？
8. **语音导演边界**：P4 是否锁定对白/旁白表演方向，还是只做音乐、环境音和音效，语音表演留到后续正式语音阶段？
9. **GLM 节点拆分**：GLM 审核与 GLM 校正使用两个独立 Text Config/Result 对，还是允许一个 GLM Config 同时输出“校正正文 + 审核摘要”？无论采用哪种，都不得由 MCP 直接改生成 Result Text。
10. **审核分歧处理**：Gemini 方案与 GLM 审核意见冲突时，哪些等级必须交给用户裁决？
11. **提示词审批**：新建/改造的提示词资产是否必须在 P4 通过前完成并审批，还是可以作为阻塞项交给下一阶段建设？
12. **原生存储粒度**：单一 P4 Markdown，还是总纲、角色、分镜单元、审核、台账分文件？
13. **Canvas 历史留痕**：Text Node 仅保存当前版本，还是需要审核区、版本差异或独立但仍为 Text 的修订记录？
14. **下游失效规则**：P4 某一角色母版或分镜设计包被修改时，是否只让引用它的下游资产失效，还是全片回退到 P4 审核？
15. **稳定标识命名**：P4 分镜单元在方案层使用 `storyboardUnitId`，还是与现有实现对齐使用 `shotId`；本草案暂不决定。
