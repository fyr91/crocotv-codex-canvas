# Continuous Learning

## Overview

改进可版本管理的指令与工作流，不修改模型权重。只把可观察证据转成候选改进，并由用户决定是否晋升为长期规则。更新时必须把能力重构进目标的既有体系，不得以追加特例代替结构整合。

## 核心原则

- **重构到既有体系**：先识别目标中的标准流程、同级概念、共享契约、执行适配层与验证方式，再把新能力放入正确的同级位置。
- **禁止默认追加特例**：如果新规则能被现有抽象表达，不得新增“特殊情况”、补充附录、独立实施章节或并行流程。
- **修改抽象，不只修改实例**：当一项改进同时影响标准流程、产物契约或多个执行后端时，先更新共享定义，再对称地更新各实施层。
- **保持单一权威来源**：规则只在负责它的层级完整定义；其他层只引用或说明差异，不复制整套规范。
- **最小化概念扰动**：优先保持体系的语义、对称性和可维护性，不以最小文本 diff 为目标。保留无关的用户改动，但应移除被新结构取代的重复和特例。
- **只改权威 Git 源**：安装在 Codex 全局目录或 Plugin cache 中的 Skill/MCP 是只读消费副本。CrocoTV 套件的长期修改只能写入 `CROCOTV_HOME` 所指 Git 仓库下的 `plugins/croco-video-factory/`，再通过提交、推送和 Plugin 更新分发；找不到该工作区时只输出修改建议。

## 固定工作流

### 1. 收集证据

只使用当前任务中可核对的材料：

- 用户纠正或明确偏好；
- 测试、验证、工具输出或实际 diff；
- 已确认重复发生的阻塞、返工或失败模式；
- 已验证成功且可复用的做法。

模型猜测、单次偶发现象和无法追溯的历史不得作为晋升证据。不得扫描无关任务或目录补凑证据。

### 2. 分类候选经验

| 类型 | 判断 | 处理 |
|---|---|---|
| 一次性上下文 | 只适用于当前任务或单次偏好 | 留在当前对话，不持久化 |
| 项目规则 | 对本项目反复适用的约束 | 提议更新最接近的 `AGENTS.md` |
| Skill 改进 | 可复用的触发条件、流程、工具或领域知识 | 提议更新现有 Skill；没有合适目标时才提议新建 |
| 未确认推断 | 缺少直接证据或适用范围不明 | 只报告疑点，不晋升 |

持久化候选必须满足以下至少一项：用户明确要求沉淀；或同类问题有两个独立、可核对的实例。满足条件只代表可以提议，不代表可以自动修改。

### 3. 定位既有体系

提议任何长期修改前，先阅读目标入口文件和受影响的直接引用，然后绘制最小必要的结构图：

1. 权威流程或顶层规则在哪里；
2. 与新能力同级的元素如何定义；
3. 共享输入、输出、状态、产物或节点契约在哪里；
4. 原生、MCP 或其他执行方式如何作为同一流程的适配层；
5. 现有内容中是否已有冲突、重复或特例补丁。

为候选改进选择正确的抽象层和同级插入点。如果既有体系无法一致表达该改进，应提议重构共享结构，不得绕过它新增一条仅服务当前实例的支路。

### 4. 输出重构审核包

每个候选使用固定结构：

1. 证据及其来源；
2. 现有体系、同级元素和权威来源；
3. 建议规则的抽象层、适用范围和重构后的目标结构；
4. 需要修改、移动、引用或删除的文件与内容；
5. 将被消除的冲突、重复和历史特例；
6. 验证方法与回滚方法；
7. 状态：`等待用户明确确认`。

没有足够证据时，输出“不晋升”及原因，不为完成闭环而制造规则。

### 5. 等待确认

修改任何长期状态前取得用户对目标文件和建议 diff 的明确确认。

- 不得静默修改 `AGENTS.md`、`SKILL.md`、Prompt 或其他持久化规则。
- 不得读取或记录密钥、凭证、个人数据或无关内容。
- 不得扩大权限、改变安全边界或把批准范围扩展到其他文件。
- 不得覆盖未纳入审核包的用户改动。

### 6. 重构并验证

用户批准后：

1. 重新读取目标文件和其作用域内指令，确认建议仍然适用。
2. 修改 Skill 时必须使用 `skill-creator`，并保留与本次重构无关的用户改动。
3. 先更新权威定义和共享抽象，再按既有层级对称更新同级元素与各执行适配层。
4. 移除已被新结构取代的重复定义、独立特例和旧支路；不得为了保持小 diff 而同时保留新旧两套表达。
5. 检查所有受影响的同级定义、下游引用、产物契约和执行后端，确认新能力已完整融入而非只在一处可见。
6. 运行目标原有验证；Skill 还需运行 `quick_validate.py` 和 `plugin-eval analyze`。
7. 有改前基线时使用 `plugin-eval compare` 比较前后结果；验证失败则回滚本次修改或提交修订后的审核包。
8. 报告已改文件、结构性变化、已消除的特例、验证结果、剩余风险和可执行回滚方式。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 每个任务结束都新增规则 | 只有明确请求或重复且有证据的问题才进入审核 |
| 把一次用户偏好升级为全局规范 | 保留为一次性上下文，除非用户明确要求持久化 |
| 自动改写自身以体现“自我进化” | 先提交审核包，等待明确确认 |
| 在文档末尾追加一个新功能的特例章节 | 找到同级元素和权威定义，重构到既有体系并删除重复表达 |
| 只在一个执行后端中定义新流程 | 先更新共享流程，再让原生、MCP 等后端按同一契约实施 |
| 为追求最小 diff 保留新旧两套规则 | 最小化概念扰动，保留无关改动但清理被取代的补丁 |
| 只改文档不验证 | 运行目标验证和 plugin-eval，并提供回滚方法 |
